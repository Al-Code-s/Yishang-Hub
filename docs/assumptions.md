> 本文件记录开发过程中的**普通不确定项、版本偏差与实施边界**。凡涉及删除数据、生产配置、
> 真实设备控制的决策**不在此自行决定**，需由项目方确认后另行记录。
> 每条假设都标注了「影响范围」与「关闭条件」，请按需复核。

## 二、本地开发用驱动

- 任务书要求 `mysqlclient` 并锁定兼容版本。**Windows 本地无 C 编译工具链**，直接安装
  `mysqlclient` 会失败，因此本地开发使用 `PyMySQL`（`DB_DRIVER=pymysql`）。
- **部署（Docker/Linux）仍使用 `mysqlclient`**，镜像内通过 `build-deps` 编译。该路径**未在本机验证**。
- 影响：`PyMySQL` 与 `mysqlclient` 在参数绑定、字符集与部分异常类型上存在细微差异。
  代码中未使用驱动私有 API，但**生产部署前需在目标环境跑一次完整测试**。
- 关闭条件：在 Docker 或 Linux CI 上以 `mysqlclient` 跑通 `pytest` 全量用例。

## 三、大小写敏感性

- MySQL 默认排序规则 `utf8mb4_0900_ai_ci` **大小写不敏感**，`SQL_MODE` 中也未逐字段声明 `_bin`。
- 任务书 5.1 要求：涉及编码、条码、设备外部标识时必须明确大小写是否敏感，
  **不能完全依赖数据库默认排序规则**。
- 本阶段处理方式：**在序列化器/服务层显式做规范化与比较**，而不是依赖排序规则：
  - 业务编码、SKU 编码、设备标识在写入前 `strip()`，并以 `casefold()` 结果做重复性业务校验。
  - 对外查询的精确匹配使用数据库唯一约束兜底，同时服务层给出明确冲突提示。
- 已知限制：若未来需要「`Abc` 与 `abc` 视为不同编码」，必须改为 `_bin` 排序规则并重建索引，
  属于破坏性变更，需单独评审。当前业务语义为**不区分大小写**，故 `_ai_ci` 语义满足需求。
- 关闭条件：随阶段 2 单据编号落地时补充「同码不同大小写」的专项测试用例。
  **部分关闭**：供应商资质证书编号已按此语义落地并有用例覆盖（`test_srm_api.py::test_qualification_certificate_no_deduplicated_case_insensitively`），
  单据编号的大小写用例仍待阶段 2 单据落地后补充。

## 四、业务与数据边界假设

1. **单企业、多工厂、多部门**。数据模型保留 `company_id` 归属，但**不宣称已完成 SaaS 多租户隔离**。
2. 库存维度中的「无批次 / 无卷号」等空值场景，**不使用含多个可空字段的联合唯一索引防重**，
   改用显式规范化维度键（见 `docs/data-model.md` 与 `docs/inventory-rules.md`）。
3. 时间统一按 UTC 存储（`USE_TZ=True`），业务界面按 `Asia/Shanghai` 展示与分组。
4. 阶段 0/1 的演示数据均为**开发种子数据**，界面与接口中一律带有模拟标识，不得当作真实业务数据。
5. 设备采集在阶段 5 实施前，**不存在任何真实硬件接入**；平台内不提供伪造的采集结果。
6. **「同一客户/供应商只能有一个主联系人」由服务层保证，不是数据库约束**：
   MySQL 不支持带条件的部分唯一索引（`UniqueConstraint(condition=...)` 在 MySQL 上不被支持）。
   规则实现在 `apps/core/services.py::ensure_single_primary`，与写入同事务执行，
   并由 `test_crm_api.py` / `test_srm_api.py` 覆盖。**不对数据库层做虚假承诺**。
7. **供应商资质证书编号的判重语义为「不区分大小写」**：`dedup_key` 使用 `casefold()`
   规范化；未填写编号时 `dedup_key` 为 `NULL`，同类型可并存多条。
   若项目方要求区分大小写或禁止重复登记同类型资质，需修改规范化函数并重建唯一索引（破坏性变更）。
8. **`tags`（标签）字段暂不提供界面编辑入口**：模型与接口支持字符串数组，
   但前端通用表单尚不支持数组字段。为避免「看着能填、实际不生效」的假输入，
   界面上不展示该字段；需要界面维护时再单独开发数组控件。
9. **准入审批尚未接入 `workflow`**：`admission_status` 当前仍是档案字段，
   **不代替审批记录**（供应商评价已落地，见 §四之十与下面 10~12 条）。

### 供应商评价的实施口径（**已按此落地**，实现见 §四之十）

10. **权重总和必须为 100%**：质量、技术、响应、交付、成本五类权重保存为配置，
    保存与启用时校验总和为 100%；权重版本变更需留痕，历史评分沿用评分时的权重快照。
11. **必须保存评分依据**：每条评分记录保存打分人、时间、原始观测值（如到货准时批次数、
    检验不合格批次数）与计算过程，不允许只存一个最终分数。
12. **无数据不得自动记零分**：某维度缺数据时，按配置选择「标注缺失」或
    「重新分配有效权重」，二者都必须在该条评分记录上体现，且对外展示时标注存在缺失维度。
    不允许把「没有数据」与「数据为零」混为一谈。
13. **停用供应商不能新建正常采购订单**：停用（`is_active=false`）或准入状态非「已准入」的供应商，
    在采购订单服务中校验拦截；确需例外时走显式授权并留痕。
    **已落地**：`procurement` 在创建 / 修改 / 提交时拦截（`SUPPLIER_NOT_USABLE`），
    持 `procurement.order.override_supplier` 且填写例外原因可例外并写审计（REQ-10.4-09）。


## 四之二、库存服务的实现假设（阶段 2 核心）

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-06 | 调整单（`adjustment`）**复用修正（`ST`）编码规则**，未新增 `AD` 规则 | 避免在编码规则表中增加仅为区分类型存在的规则；若业务需要单独的盘点/调整号段，需新增规则并回填历史单据 |
| A-07 | 批次号/卷号**不区分大小写**（`casefold()`） | 符合任务书 5.1「明确大小写是否敏感」的要求；已文档化并测试（`test_batch_no_is_case_insensitive`）。若业务上存在区分大小写的合法批次，需改为保留原样 |
| A-08 | 冲销（`reverse`）采用「**原单反向流水 + 状态标记**」，不修改原流水 | 符合任务书 5.5「不做原地改数」；冲销前必须确认下游未消耗，否则拒绝 |
| A-09 | 库存余额**只保存数量，不保存金额** | 移动加权平均属阶段 7 「基础成本」；本轮不伪造已完成成本核算 |
| A-10 | 服务层**始终拒绝负库存**，忽略 `Warehouse.allow_negative_stock` | 字段已建模但未接入判定；若要开放，必须补充显式授权与审计，不能仅靠字段放行 |
| A-11 | 跨仓调拨**暂不支持**，调拨以同仓移库实现 | 在途状态与目标仓确认流程尚未建模；不伪造「已实现调拨」 |

## 四之三、采购模块的实现假设（阶段 2 采购增量）

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-12 | `PurchaseOrder.tax_rate` 采用**百分数**（0~100），不是小数比率 | 与页面字段「税率(%)」一致，避免 13% 被写成 0.13；若业务要求小数比率，需迁移历史数据并改前端 |
| A-13 | 订单金额按**行金额四舍五入到 4 位小数后求和**，再算税额、价税合计（`ROUND_HALF_UP`） | 明确「舍入发生在哪一步」；与「先合计再舍入」在某些单据上会差 0.0001，如有对账要求需先确认口径 |
| A-14 | **账期/结算方式**只作为文本字段（`payment_terms`），不做账期计算与到期提醒 | 应付与账期管理属阶段 7；本轮不伪造财务能力 |
| A-15 | 收货单**只能引用采购订单行**，不支持无订单的「直接收货」 | 保证「实收到货」都有来源可追溯；若存在零星采购/无单收货场景，需新增来源类型并单独授权 |
| A-16 | 采购收货**只进一个仓库**（单据头级 `warehouse`），行级可选择储位 | 与「一次到货落一个仓」的实际操作一致；跨仓收货需拆成两张收货单 |
| A-17 | 来料检验是**人工判定**，且一次判定作用于**整张收货单的所有行** | 未接入检测设备，无法取得自动判定；若要按行分别判定（部分合格部分不合格），需改为行级判定并拆分库存单据 |
| A-18 | 收货过账后的待检库存**不参与占用**（`reserved`） | 采购侧到货尚未成为可分配供给；占用由销售订单与工单驱动 |
## 四之四、销售模块与库存占用的实现假设（阶段 2 销售增量）

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-19 | 销售订单的**发货仓库在订单头**（`SalesOrder.warehouse`）；未指定仓库时**拒绝占用与发货** | 占用必须落到明确的仓库维度；若要「按订单行指定仓库」，需改为行级字段并同步占用、出库与退货逻辑（错误码 `ORDER_WAREHOUSE_REQUIRED`） |
| A-20 | 占用维度（储位 / 批次 / 卷号）由 `stock.choose_reservation_dimension` **自动挑选可用量最大的合格维度**；同一物料分散在多个维度时报 `STOCK_SPLIT_ACROSS_DIMENSIONS` | **不做跨维度自动拆分占用**，避免「一次占用写多行」带来的部分失败与释放规则复杂化。如需自动拆分，必须新增可追溯的分配模型并重新定义释放口径 |
| A-21 | 销售发货**必须先占用**（出库一律 `require_full_reservation=True`） | 保证「已承诺给某订单的数量」不会被别的订单抢走；未占用直接发货返回 `RESERVATION_REQUIRED`。这比任务书要求更严，若业务上希望「先到先发」，需显式降级并说明 |
| A-22 | 占用**不写库存流水**，一致性口径为 `InventoryBalance.reserved == 该维度未结占用之和` | 流水只记实存量增减，便于对账；占用结束区分 `closed`（被消耗）与 `cancelled`（被释放），可追查「占用去哪了」 |
| A-23 | 退货行未填储位 / 批次 / 卷号时，**继承原发货出库单据的维度并写回退货行** | 批次追溯不断链，检验放行复用同一维度；若原发货行维度为空（历史数据），退货会因维度不全被拒绝，需人工补齐 |
| A-24 | 可退数量按**「已发货 − 已退货」总量**控制，不按批次分摊 | 首版不建模「退回的是哪个批次的货」，多批次部分退货的批次级分摊留待后续；当前以继承原发货维度为准 |
| A-25 | 销售订单**未建模折扣与订单变更版本快照**（只有单价 + 税率，金额后端算） | 任务书 10.3 的折扣、订单变更版本快照未实现，**不伪造**；已列入 `docs/progress.md` 与本文档 §六未做清单 |

## 四之五、BOM 与工艺路线版本快照的实现假设（阶段 3 第一步）

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-26 | 含损耗用量口径为 `gross_quantity = 净用量 × (1 + 损耗率)`，损耗率取值 `[0, 1)` | 任务书 9.5 只要求「标准用量、损耗」，未定义公式方向。另一常见口径是 `净用量 ÷ (1 − 损耗率)`（结果更大）。若企业实际按后者，**只需改 `BomLine.gross_quantity` 一处**（舍入已收敛在该属性内），但历史版本的已下达工单快照不会自动重算，需人工评估 |
| A-27 | 「同一款式/SKU 范围同时只有一个生效版本」由**服务层**保证（`transaction.atomic()` + `select_for_update`），不依赖数据库索引 | MySQL 没有部分唯一索引（`UNIQUE ... WHERE status='approved'`），无法用索引兜底。风险：绕过服务层直接改 `status` 会破坏该约束；已通过「模型不提供状态写入路径 + 视图必须走服务」约束，但**未做并发用例** |
| A-28 | 替代料行**必须**指向同一 BOM 内的正常用料行（`substitute_for`），不建模「整行替换式 BOM」 | 首版按「主料 + 可替代料」表达；若需要「A 方案 BOM / B 方案 BOM」并存，应使用不同的 `scope_key`（SKU 差异版本）或新增方案号字段 |
| A-29 | 工艺路线用文本 `workcenter` / `equipment_requirement` 记录工作要求，暂不与 `factory.Station`、阶段 4 的设备主数据建外键 | 阶段 4 才有设备台账；提前建外键会把未完成的模块耦合进来。阶段 4 落地时补外键并写数据迁移，届时旧的文本字段保留为展示用 |
| A-30 | 工单版本快照**尚未落库**：本轮只提供 `build_bom_snapshot()` / `build_routing_snapshot()` 的不可变输出 | 快照归属方是 MES 工单（阶段 3 后续增量），按任务书 20.3「不建空壳」的要求不预先建空表；因此必测案例 13「BOM 历史快照不受修改影响」当前以「**已审核版本内容不可修改 + 派生新版本后旧快照不变**」的方式验证 |

## 四之六、MRP 的实现假设（阶段 3 第二步）

> 编号接 §四之五 的 A-30，从 **A-31** 开始。这些假设同时写在 `MrpRun.parameters` 快照里，
> 因此历史运行可以复现当初口径（`docs/data-model.md` §三 planning）。

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-31 | **批量规则为 lot-for-lot**：净需求多少就建议多少，**不做批量合并**、**不设安全库存缓冲**、**无提前期**（需求日期即建议交期） | 首版没有供应商交期与产能约束数据，凭空设置提前期会伪造准确性。影响：建议可能高于实际最优批量；后续接提前期/批量规则时，只需在净算处新增规则层，历史运行快照不受影响（`parameters.lead_time_mode` 已固化为 `lot_for_lot`） |
| A-32 | MRP 的**需求来源只有销售订单**（`demand_sources=['sales_order']`），生产计划 / 预测 / 安全库存补货均不产生需求 | 销售模块已在阶段 2 第四步落地，是唯一有真实数据的来源。影响：MRP 结果只反映已批准订单，不是完整供需平衡；新增来源时需在 `_collect_demands()` 增加分支并同步 `parameters` |
| A-33 | **在制供给取 MES 已下达 / 生产中工单的未完工数量**（`in_progress_supply='mes_open_orders'`）；**草稿工单不计入** | 阶段 3 第三步 MES 落地后，净算把 `ON_ORDER` 与 `IN_PROGRESS` 同时纳入 `inbound_by_bucket`（`mrp._in_progress_supplies()`）。草稿工单尚未冻结 BOM / 工艺、可能被改写，把它当供给会高估可用产能。影响：在制供给的准确性取决于工单计划数量是否被认真维护 |
| A-34 | 替代料**不参与净算**：BOM 展开只取 `line_type=normal` 的行（`include_substitutes=false`） | 替代料是否可用取决于现场与实际库存，盲目把替代料计入供给会低估缺料。影响：有替代料方案的物料会显示为缺料，需人工按替代方案处理 |
| A-35 | 展开用量取 **`gross_quantity`（含损耗）**，不做二次损耗叠加 | `gross_quantity = 净用量 ×(1+损耗率)`（见 A-26），含损耗用量已经是"生产 1 件实际要投的量"。影响：若企业损耗口径是按工序累计而非单行，需要改为路线级损耗模型 |
| A-36 | **可用量 = `on_hand − frozen − reserved`**，且**只统计 `quality_status=qualified`** 的库存（`frozen_and_reserved='excluded_from_available'`） | 冻结与占用是"已被承诺/被锁定的量"，不能再次作为自由供给；待检 / 不合格库存不能直接投产或销售（任务书 10.8）。影响：MRP 与销售的占用口径必须保持一致，`docs/inventory-rules.md` 为唯一口径来源 |
| A-37 | 生产建议转单生成**草稿 MES 工单**，**不自动下达**，不生成工序与用料 | MES 已于阶段 3 第三步落地，`convert_suggestion()` 的生产分支改为生成真草稿工单（`source_type=mrp_suggestion` + `source_no` + `DocumentLink`）。下达会冻结 BOM / 工艺快照并生成工序与用料，是**独立动作**，由计划员确认后触发——转单不等于承诺产能（任务书 9.5）。影响：转单后仍需人工下达；旧错码 `PRODUCTION_ORDER_NOT_IMPLEMENTED` 已随分支打开而废弃 |
| A-38 | 采购建议转单只创建**草稿**采购申请，**不自动提交审批**、**不直接生成采购订单** | 审批与库存/采购承诺是不同动作（任务书 10.1）。影响：转单后仍需人工提交与审批；这是刻意设计，不是缺陷 |
| A-39 | **默认需求区间 90 天**（`DEFAULT_HORIZON_DAYS=90`），`bucket=week` 时分段键**归一到周一** | 服装企业常见备料周期；区间与分段均可由调用方指定并写入快照。影响：超出区间的需求被忽略（`test_demand_outside_horizon_ignored`），需要更长区间时显式传参 |
| A-40 | `MrpDemandLine` **不自关联**，来源追溯用 `source_type` + `source_id` + `source_no` + `path` 组合表达 | 自关联会引入递归查询与级联删除风险，且需求行只用于展示与追溯。影响：多级追溯需要解析 `path` 字符串（格式 `父件编码>子件编码`），不提供递归 SQL 查询 |
| A-41 | 「同一建议不得重复转单」由**服务层状态机 + `select_for_update`** 保证，数据库层只保证「同一运行内行号唯一」 | MySQL 无法用部分唯一索引表达"仅当 status=open 时唯一"。影响：绕过服务层直接改状态会破坏该约束；**未做真实多连接并发转单用例**（列入 `docs/test-report.md` §16.7） |
| A-42 | 归档运行（`archived`）后其建议**不可再转单**，且**不物理删除**任何 MRP 运行 / 需求行 / 供给行 / 建议 | 任务书 5.5：已过账单据不得物理删除、审计与流水不可修改；MRP 运行是可复现的历史快照，删除会让已转单的建议失去依据。影响：数据量随时间增长，后续需要归档清理策略（阶段 7 运维） |
| A-43 | 序列中的 `SO-DEMO-0002`（成品无 BOM，120 件）**保留**为演示"成品缺 BOM"告警的数据 | 它会让 MRP 的 `unexploded_materials` 非空，这是**故意**的演示数据，用于展示"成品没有生效 BOM 时不展开、只告警"的行为。影响：真实部署若不需要该告警，应停用该演示单据 |
| A-44 | MRP **不计算成本**，建议只给数量与日期 | 基础成本属阶段 7（任务书 10.16），本轮不伪造金额。影响：采购建议无法按金额排序 |

## 四之七、设备 / 能源 / 生产物流 / 安全环保的实现假设（阶段 4~6 首块）

1. **备件现存量只读自仓储。** 设备模块不建库存表、不写库存余额；
   「库存台账」是把 `wms` 的库存余额与备件的安全库存 / 寿命拼起来的**只读视图**。
   若仓储没有对应物料的库存维度，页面会显示 0 而不是报错。
2. **备件采购不另立单据。** 「备件采购申请」直接复用 `procurement.requisition`，
   因此**没有**「设备专用紧急采购审批流」这条独立流程；计划采购与紧急采购靠申请单上的
   `requisition_type` 区分（既有能力）。
3. **EHS 与设备台账是两套表。** 特种设备检验、安全检查引用设备台账，但**不写设备表**，
   也不自动回写设备状态；安全检查发现问题**不会自动生成隐患单**（需要人工登记），
   避免跨模块隐式副作用（与 `AGENTS.md` §三 4 一致）。
4. **缺陷等级 / 隐患等级 / 事故等级是各模块独立枚举**，没有做「统一风险分级字典」。
   跨模块的风险报表需要在后续阶段统一口径。
5. **能源计量口径按行业常用默认值**：
   - `multiplier`（倍率）默认 1，用于带互感器的电表；用量 = （本次读数 − 上次读数）× 倍率；
   - 首次抄表（没有上次读数）用量记 **0**，不把表底值当用量；
   - 读数回退（低于上次读数）**直接拒绝**，换表 / 清零请新开仪表，避免把负数用量写进报表；
   - 分时段（尖 / 峰 / 平 / 谷）**靠在抄表时选择时段**，不做电表内部时段解析；
   - 计价 = 各时段用量 × 该时段生效单价之和，未维护单价时**费用记 0 并标记「未维护单价」**，不猜价格。
6. **报警去重窗口是「同仪表 + 同类型 + 同一天」。** 同一天内重复越限只保留第一条，
   避免抄表频率高时刷屏；跨天会重新报警。
7. **离线判定用「抄表超时」而不是设备心跳。** 只有配置了 `offline_minutes` 的阈值才会参与扫描，
   没有配置的仪表不检测（避免「全表报警」）；扫描由 `manage.py ems_offline_check` 或
   `POST /api/v1/ems/alarms/scan-offline/` 触发，**平台没有内置调度器**，需要部署侧配计划任务。
8. **单耗（unit_consumption）= 能耗 ÷ 产量。** 产量为 0 时单耗记 0 且不触发单耗报警
   （没有产量就没有单耗口径，不伪造）。
9. **物流任务与设备状态联动是单向的。** 任务开始 → 设备「作业中」，任务完成 / 取消 → 设备「空闲」；
   但**设备被手工置为故障不会自动取消执行中的任务**（需要人工取消），避免自动化误伤在途作业。
10. **同一设备同时只允许一个执行中的任务**，没有做「多任务排队」。
11. **作业许可的监护人要求是硬校验**：动火、防爆防静电、受限空间三类必须指定监护人才能批准；
    检维修作业不强制。
12. **四个新模块的编号取号依赖编码规则表**（`core_coderule`）。测试库不跑 `bootstrap_system`，
    所以用例里显式建规则；**部署时必须执行 `bootstrap_system`**，否则新增单据会报
    `CODE_RULE_NOT_FOUND`（这是刻意设计，不静默生成编号）。
13. **设备数采首版只做 HTTP 上报 + 内置模拟器。** 连接配置里的 `mqtt` / `modbus` 是**待协议确认**的选项，
    采集入口对未实现的协议直接返回 `PROTOCOL_NOT_IMPLEMENTED`（409），不做「界面能配、数据进不来」的假适配；
    协议适配与真实设备联调未做（见 §五 A-02）。
14. **设备令牌只存摘要。** 网关令牌以 SHA-256 摘要落库（`token_hash`），明文只在生成 / 轮换的响应里返回一次，
    轮换后旧令牌立即失效；平台**不复用员工登录会话**做硬件上报（`ingest` 入口显式关闭会话认证）。
15. **数采读数不写能源抄表。** 测点可以关联能源仪表作为「对照线索」，但采集读数**不会**变成 `MeterReading`，
    避免与人工抄表重复计量；越限 / 离线报警统一调用 `apps/ems/services.py::raise_alarm` 落到能源报警台账，
    并用 `source_ref` 记录来源测点，使去重窗口从「同仪表 + 同类型 + 同一天」细化为
    「同仪表 + 同类型 + 同来源 + 同一天」。
16. **模拟设备不参与离线判定。** `detect_offline_gateways()` 跳过 `is_simulated=True` 的设备，
    否则演示数据会被判成大面积离线；模拟读数也**不计入**真实产量与能耗口径。
17. **采集读数只带测点编码与数值**，单位与物理量由测点定义；平台不对测点含义做自动推断
    （传感器物理量分配未明确，见 §五 A-01）。
18. **客户投诉与产品评价的口径**：投诉「受理 → 处理 → 关闭」只能走动作接口（跳步 409），
    关闭前必须填处理措施（空措施 400），满意度 0 = 未评价、1~5 = 评分；
    产品评价评分 1~5（越界 400），回复与关闭同样走动作接口。
    状态字段一律只读，每次流转写审计日志（`record_audit`），**不另建日志表**。
    **未做**：投诉外部渠道自动接入、投诉自动分派与投诉统计报表。
19. **统计一律按明细实时聚合，不落汇总表。** 数采采集统计（`apps/iot/selectors.py`）与投诉 / 评价统计
    （`apps/crm/selectors.py`）都直接读明细：设备会补发、会重传，汇总表在一次补发后就会与明细对不上。
    代价是数据量增长后查询变慢，届时应先补归档 / 分区，而不是先加一张对不上账的汇总表。
20. **分桶按业务时区，用偏移量而不是 `CONVERT_TZ`。** 数采统计把 `device_time` 先加上业务时区偏移再
    `TruncDay` / `TruncHour`，取桶时再减回偏移还原成 UTC 时刻返回。原因：本项目的 MySQL 实测**未导入
    命名时区表**，`TruncDay(..., tzinfo=...)` 生成的 `CONVERT_TZ` 会返回 `NULL`，整张统计表会静默空掉。
    Asia/Shanghai 不实行夏令时，偏移量恒为 +08:00，因此安全；**若换用有夏令时的时区，需改用带时区表的实现**。
    另外，日期型参数（如统计的 `until`）按业务时区解析，`until=当天` 含当天整天，
    不会因为 `datetime.fromisoformat` 接受纯日期而退化成当天 00:00。

## 四之八、质量管理（QMS）的实现假设

21. **检验结论不允许被客户端指定。** 定量项目（有上下限）的 `is_qualified` **只由服务层按标准区间计算**，
    请求里携带的结论被直接忽略；定性项目必须由检验员给出结论。判定时再校验一次：
    存在不合格项不能判「合格」、全部合格不能判「不合格」、判「让步接收」必须写清原因。
    这样「粉饰结果」与「跳步」都会在接口层被拒，而不是靠人自觉。
22. **检验结果的声明口径是「覆盖」而不是「追加」。** 同一检验单同一项目在库里只有一条
    （`uq_qms_result_order_item`），重复录入即覆盖；**判定之后不允许再改结果**（409）。
    需要修正历史结论请新建检验单，已判定的单据不被改写。
23. **不合格自动报警，但同一检验单只报警一次。** `judge_order` 判定为不合格时生成
    `QualityAlert`（级别按不合格项数量分级：1 项轻微 / 2 项严重 / ≥3 项致命），
    若该单已有报警则复用，不重复创建；**报警未闭环时检验单不允许关闭**，
    避免「点一下就算处理完」。报警是 QMS 自己的台账，**不复用能源报警台账 `ems`**：
    两者的处理人、闭环语义与页面都不同，混用会让能源看板出现质量报警。
24. **检验标准不落版本快照（已知缺口）。** 检验单保存受检对象与来源单据，但不保存项目标准的历史快照，
    因此**改标准会影响历史单据的解读**。这是本轮明确未做项（见 `docs/requirements-matrix.md` REQ-10.9-02/08），
    落地「面向物料的检验标准集 / 版本」时需要补一张快照表，不能靠现有字段假装已实现。
25. **QMS 与既有质量路径并行，不做隐式联动。** `procurement.receipt.inspect`（收货单人工判定）与
    `wms` 的质量放行仍按原样工作，QMS 检验单通过 `source_no` 引用来源单据，
    **不会**自动改写采购收货或库存的质量状态；两者接线（含按工艺路线 `is_quality_gate` 决定质检点）
    需要 MES 落地后显式发起，避免出现「两个模块都能改同一张单据状态」的隐性耦合。
26. **检验结果全部人工录入。** 当前**没有**检测仪器 / 在线检测分析设备的采集接口
    （见 §五 A-01 同类问题），因此「质量在线检测」在本版本等于「按标准在线判定 + 留痕」，
    不宣称已接入任何检测设备。
27. **质量统计只按明细实时聚合。** 统计口径刻意如此：**合格率的分母只含「已判定且不是待判定」的单据**，
    草稿与已提交未判定不计入（否则「还没检验」会被算成不合格，合格率凭空变低）；
    「让步接收」单列，不并入合格也不并入不合格。与数采 / 客户服务统计同一口径，**不落汇总表**。


## 四之九、生产执行（MES）的实现假设

28. **工单下达即冻结快照，快照不单独建表。** 下达瞬间把生效的 BOM 与工艺路线冻结进
    `ProductionOrder.bom_snapshot` / `routing_snapshot`（JSON），并据此展开工单用料与工序；
    之后工程数据出新版本**不影响已下达工单**（A-19 同一口径）。
    快照生命周期与工单一致，单独建表只会多一次 join（`docs/architecture.md` ADR-08）。
29. **工单表头在非草稿状态下冻结。** 下达及之后的 `PATCH` 返回 **409 `STATE_CONFLICT`**；
    要改数量或排期请新建工单，**不把已下达工单改来改去**。用料行只能在草稿阶段手工增删。
30. **报工只追加，不可回改。** 报工台账（`ProductionReport`）无修改接口，也不提供删除；
    填错了就补一条**返工报工**，而不是把历史数字改掉。数量口径由服务层校验：
    合格 + 返工 + 报废 = 报工量（`QUANTITY_MISMATCH`），同一工序累计报工不得超计划（`OVER_PRODUCTION`）。
31. **完工数量取末道工序，报废取全工序之和。** 同一件产品会经过多道工序，
    按工单汇总所有工序报工会**重复计数**，因此 `completed_quantity` / `qualified_quantity`
    取末道工序（`sequence` 最大者）的累计合格数；`scrap_quantity` 则是全部工序报废之和（报废发生在哪道都算损失）。
    工序级良率与 OEE **本轮未算**（需设备运行时长，属后续增量）。
32. **质检点是完工的硬门槛。** `is_quality_gate=True` 的工序报满时（累计报工 ≥ 计划数量）
    自动开一张 QMS 检验单（内部校验 `qms.inspection.create`）；工单完工前，
    全部质检点工序的检验单必须已判定为「合格」或「让步接收」，否则 `QUALITY_GATE_NOT_PASSED`（整笔回滚）。
    未判定 / 已提交未判定 / 不合格均不放行——「先完工再补检验」在接口层就被拦住。
33. **领料与完工入库只能经统一库存服务。** MES 不写库存余额与流水，
    而是调 `apps/wms/services/stock.py` 生成并过账出 / 入库单（`issue_document` / `receipt_document` 保留链路）；
    重复提交靠 `Idempotency-Key` 保平，已领 / 已入库再次请求报 `MATERIAL_ALREADY_ISSUED` / `RECEIPT_ALREADY_POSTED`（409）（`docs/inventory-rules.md`）。
34. **MRP 的在制供给只认已下达 / 生产中工单。** 草稿工单不计入在制供给（A-33）；
    因此「转单」本身不会立刻减少净需求，要等工单真正下达后才计入——避免用草稿工单把不存在的产能当成供给。
35. **本轮未做（不得视为已有）：** 线体排产、裁剪任务 / 裁片批次、工位派工、
    在制品转移与返工工单、报工扫码 / RFID 与硬件控制（无协议不伪造）、
    按工序核算良率 / OEE、工单成本。详见 `docs/requirements-matrix.md` §10.7。

## 四之十、供应商五维量化评价的实现假设（本轮）

36. **总分只能由服务层算，客户端传的分数一律忽略。** `total_score` 由 `srm.services.recalculate`
    按权重快照计算，接口请求里携带的 `total_score` / `grade` 不生效
    （与 QMS「定量项目结论由服务层判定」同一口径：不允许人工填一个好看的分数）。
37. **权重配置只增不改，评价单冻结权重快照。** 调整权重会**派生新版本**（`version_no` 自增，
    旧版本原样保留、可追溯），`PATCH` 的响应体是新那条；评价单在建单时保存
    `weight_snapshot`，**历史评价不因后来改权重而变化**。若项目方要求「改权重即时影响历史评价」，
    需改成引用式取权重并放弃可解释性——本版刻意不这样做（A-10）。
38. **五个维度必须各给一行，「没填」与「0 分」强制区分。** 没有数据的维度把 `raw_score` 留空，
    服务层标记 `is_missing=True`、有效权重 0、加权得分为 `NULL`；打了 0 分则是 `raw_score=0.00`、
    照常计入。缺失维度写入 `missing_dimensions` 并在界面标红，**不把没有数据当成 0 分**（A-12）。
39. **缺数据的两种口径语义不同，界面与文档都如实说明。**
    「标注缺失」不重分配权重，总分是**不完整口径**（上限低于 100），因此**不给等级**；
    「重新分配有效权重」把缺权重按比例摊给有数据的维度、**合计精确等于 100%**
    （四舍五入余量补在权重最大的维度上），总分是完整百分制、可以给等级。
    切换口径会立即用同一批明细重算，不会留下「口径与结果不一致」的中间态。
40. **评价生效后不可改，只能归档。** `draft → effective → archived` 由 `publish` / `archive`
    动作推进，跳步与重复推进一律 409；已生效评价的明细与表头都不可改（`EVALUATION_LOCKED`）——
    要修正请归档后重新发起，历史因此始终可核对。
41. **评价统计只按明细实时聚合，且不把不完整口径混进平均分。** 平均分只在
    「口径完整（有等级）」的评价上求平均；缺数据的条数（`ungraded_total`）与
    缺失维度行数（`line_missing_total`）单独返回；维度均值按「有数据的行」计算，
    没有样本时返回 `null` 而不是 0（与 QMS / 客户服务 / 数采统计同一口径，**不落汇总表**）。
42. **本轮未做（不得视为已有）：** 供应商寻源与候选供应商、准入审批接入 `workflow`、
    可供物料与报价及有效期（与采购价联动）、检测仪器直连评分数据。
    详见 `docs/requirements-matrix.md` §10.4 与 §一之二十三。
43. **平台只服务一家公司（`XJYS`），旧演示公司已下线。** 早期 `seed_demo` 建的
    第二家公司及其演示数据（工厂 / 部门 / 员工 / 物料 / 库存 / 采购 / 销售 / MRP 等）
    已于 2026-09-22 整体清理，`factory.Company` 只保留「新疆意尚智造科技有限公司」；
    角色与账号改挂到该公司，员工编号 `E1xxx` 等旧档案不再存在。
    `seed_demo` 保留命令名但等价于 `seed_demo_xjys`。影响范围：开发库数据与演示命令；
    关闭条件：不再需要旧演示数据（如需回退，用 `.tmp/backup/` 的 `mysqldump` 备份恢复）。

## 四之十一、生产安装与内网部署的假设（本轮新增）

44. **首次安装必须显式初始化，`migrate` 不会建出可登录的系统。** 空库执行 `migrate` 只得到
    空的表结构：权限点 / 菜单 / 内置角色 / 管理员账号由 `manage.py bootstrap_system` 建立
    （幂等，可重复执行，生产环境必须有 `YISHANG_ADMIN_PASSWORD` 或 `--admin-password`），
    Django Admin 与 DRF 的静态资源要先 `manage.py collectstatic` 收进 `backend-static` 卷，
    Nginx 的 `/static/` 才命中。因此漏掉前者的现象是「登录不上」，漏掉后者的现象是
    「主平台正常、`/admin/` 样式与脚本 404」（前端页面是打进 Nginx 镜像的构建产物，不受影响）。
    演示数据命令 `seed_demo` / `seed_demo_xjys` 在 `DJANGO_ENV=production` 下**直接拒绝执行**，
    **不得**用于客户机初始化。影响范围：生产首次安装流程；关闭条件：安装步骤不再需要人工执行。
    步骤已写入 `docs/deployment.md` §三「首次安装（空库）必做步骤」。

45. **内网纯 HTTP 部署当前不可用（已知限制，本版本未做环境开关）。** 生产配置
    `backend/config/settings/prod.py` 把 `SESSION_COOKIE_SECURE` 与 `CSRF_COOKIE_SECURE` 硬编码为
    `True`（只有 `SECURE_SSL_REDIRECT` 能通过 `DJANGO_SECURE_SSL_REDIRECT` 关闭）。因此在
    「只能 HTTP 访问、没有证书」的客户内网机器上，关掉重定向后登录页能打开，但**浏览器不会在
    HTTP 下回传会话 Cookie**，表现为「登录后立刻退回登录页」或 CSRF 校验失败。可行的落地方式两种：
    ① 给 Nginx 配 TLS（自签证书或客户内网 CA），保持默认安全配置；
    ② 把这两个开关改成环境变量驱动（默认仍为 `True`），仅在客户明确接受「纯内网 HTTP」风险时用 `false`。
    **本版本只做了 ① 的判断依据，未实现 ②**，因此纯 HTTP 客户机需要先定方案再上线。
    影响范围：生产部署方式；关闭条件：完成 ① 的 TLS 配置或 ② 的环境开关改造。
    **2026-09-24 更新**：已实现方式 ②——`prod.py` 增加 `DJANGO_COOKIE_SECURE` 开关（**默认仍为 `True`**，
    不改变任何现有安全默认值），`SESSION_COOKIE_SECURE` 与 `CSRF_COOKIE_SECURE` 都由它控制，
    并已在 `compose.yaml` 透传。因此纯内网 HTTP 部署只需在根目录 `.env` 里把
    `DJANGO_SECURE_SSL_REDIRECT=false` 与 `DJANGO_COOKIE_SECURE=false` 一起设置即可登录。
    风险不变：关闭后 HTTP 上的会话不再有 Secure 保护，**仅限内网、且需项目方明确接受**；
    仍是 ①（配 TLS）更安全。

46. **数据库版本基线由「MySQL 8.4 LTS」调整为「MySQL 8.0 系列」（项目方 2026-09-23 确认）。**
    任务是让部署版本与本地开发库（8.0.17）落在同一主版本，减少「开发能跑、上线报错」的版本差异；
    部署镜像相应改为 `mysql:8.0`（**8.0 系列最新补丁，不钉死小版本**），不使用任何 8.4 专属语法。
    依据：代码与迁移里没有 8.0.17 之后才具备的特性（检索过 `JSON_VALUE` / `JSON_TABLE` /
    `INTERSECT` / `EXCEPT` / `LATERAL` / `NOWAIT` / `SKIP LOCKED` 均无使用），
    实际用到的能力下限是 `utf8mb4_0900_ai_ci`（8.0.0+）与 CHECK 约束（8.0.16+）；
    测试强制跑在真实 MySQL 上（`config/settings/test.py`），本机 8.0.17 全量用例通过。
    **两条运维约束**：① MySQL 8.0 不支持从 8.4 的数据目录降级启动，
    已有 8.4 数据必须走 `mysqldump` 逻辑导出后再导入；② 8.0 系列的官方支持窗口到 2026-04 结束，
    因此镜像取 8.0 系列最新补丁而非 8.0.17。影响范围：数据库版本口径与部署镜像；
    关闭条件：项目方再次调整版本基线。同步更新了 `PROJECT_SPEC.md`、`README.md`、
    `docs/deployment.md`、`docs/requirements-matrix.md`、`docs/progress.md`、`docs/test-report.md`、
    `docs/acceptance.md` 与前端「进度说明」页的版本描述。
47. **开发库口令与数据快照改为随 Git 仓库走（项目方 2026-09-24 确认，有意偏离 AGENTS.md 第二条）。**
    项目方明确：本仓库是**单人私有仓库**，平台只服务一家公司、开发数据均为演示数据，
    不存在需要保护的第三方资料；为了让「换电脑 = `git clone`」成立，把 `backend/.env`
    （开发库口令、`DJANGO_SECRET_KEY`、初始化口令）与 Compose 用的根目录 `.env`
    （容器 root 口令、`HTTP_PORT` 等）都取消忽略并入库，并把 `mysqldump` 快照放进 `db/`。
    AGENTS.md 第二条关于**生产**的要求不变：生产口令只从环境变量注入，
    `deploy/`、`compose.yaml` 与文档中不得出现任何真实生产口令。
    两条必须守住的约束：① 生产库口令**不得**与开发库口令相同；
    ② 一旦仓库转为公开或新增协作者，必须先 `git filter-repo` 把 `backend/.env` 从历史中移除并轮换口令。
    影响范围：仓库内容与本地开发配置；关闭条件：仓库公开化或加入协作者。

49. **容器里「一次性命令」与「Web 进程」用的是两套设置（本版本未统一，已记录未改）。**
    `config/wsgi.py`（gunicorn 的入口）默认 `config.settings.prod`，但 `manage.py` 与
    `config/celery.py` 默认 `config.settings.dev`，而 `compose.yaml` 只注入 `DJANGO_ENV`、
    **没有注入 `DJANGO_SETTINGS_MODULE`**。因此容器内 `migrate` / `collectstatic` /
    `bootstrap_system` 等命令与 `worker` / `beat` 实际按 dev 口径运行：① `bootstrap_system`
    不会因缺少 `YISHANG_ADMIN_PASSWORD` 而失败，而是**随机生成并打印一次**；②
    `seed_demo` / `seed_demo_xjys` 的「生产环境直接拒绝」拦截不会触发（它判的是
    `settings.DJANGO_ENV == "production"`）。**功能上不阻塞**（迁移与设置无关，Web 进程也不是 dev），
    但「生产环境绝不自动生成口令」「生产环境拒绝演示数据」这两条保证在容器里要靠人工纪律。
    影响范围：Docker 部署的一次性命令与后台任务；关闭条件：在 `x-backend-env` 里加
    `DJANGO_SETTINGS_MODULE: config.settings.prod` 并复验（**本轮未改、未验证**，
    已写入 `docs/deployment.md` §三「容器里的一次性命令用的是哪套设置」供项目方决定）。

48. **国内网络下 Docker 构建与拉取需要「可配置的软件源」和「可用的镜像加速器」（环境相关，非代码缺陷）。**
    实测（2026-09-24，项目方 Windows + Docker Desktop）：`docker compose build` 的 `runtime` 阶段
    `apt-get update` 对官方源 `deb.debian.org` 间歇性返回 `502 Bad Gateway`（同一时刻 `builder`
    阶段的同一条命令却成功），导致 `target backend: failed to solve ... exit code: 100`；
    Docker Desktop 里配置的 `registry.docker-cn.com` 加速器已停止服务，
    使本地镜像 `yishang-platform-*:local` 也被当成远端拉取而报 `EOF`。
    处理：`deploy/docker/Dockerfile.backend` 的 apt 源改为构建参数 `APT_MIRROR`（默认官方源，
    根目录 `.env` 可改成国内镜像）；镜像加速器**必须由使用者在 Docker Desktop 里自行删除**，
    仓库无法代改。同一类问题在前端镜像里也存在：`Dockerfile.frontend` 的 `npm ci` 发生在
    `frontend/.npmrc` 被复制进镜像之前，走的是 npm 官方源，因此增加 `NPM_REGISTRY` 构建参数
    （默认空 = 官方源，行为不变）。本条的假设仍是「构建机 / 部署机能访问所选软件源与镜像仓库」，
    只是不再假定官方源直连可用；关闭条件：网络环境改善，或把 `APT_MIRROR` 改回 `deb.debian.org`。
    影响范围：Docker 构建与拉取；同步更新了 `compose.yaml`、`deploy/docker/Dockerfile.backend`、
    `.env.example`、`docs/deployment.md`、`docs/progress.md`。
