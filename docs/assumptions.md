# 假设与偏差（docs/assumptions.md）

> 本文件记录开发过程中的**普通不确定项、版本偏差与实施边界**。凡涉及删除数据、生产配置、
> 真实设备控制的决策**不在此自行决定**，需由项目方确认后另行记录。
> 每条假设都标注了「影响范围」与「关闭条件」，请按需复核。

## 二、本地开发用驱动

- 任务书要求 `mysqlclient` 并锁定兼容版本。**Windows 本地无 C 编译工具链**，直接安装
  `mysqlclient` 会失败，因此本地开发使用 `PyMySQL`（`DB_DRIVER=pymysql`）。
- **部署（Docker/Linux）仍使用 `mysqlclient`**，镜像内通过 `build-deps` 编译。该路径**未在本机验证**。
- 影响：`PyMySQL` 与 `mysqlclient` 在参数绑定、字符集与部分异常类型上存在细微差异。
  代码中未使用驱动私有 API，但**生产部署前需在目标环境跑一次完整测试**。
- 关闭条件：在 Docker 或 Linux CI 上以 `mysqlclient` 跑通 `pytest` 全量用例。

## 三、大小写敏感性

- MySQL 默认排序规则 `utf8mb4_0900_ai_ci` **大小写不敏感**，`SQL_MODE` 中也未逐字段声明 `_bin`。
- 任务书 5.1 要求：涉及编码、条码、设备外部标识时必须明确大小写是否敏感，
  **不能完全依赖数据库默认排序规则**。
- 本阶段处理方式：**在序列化器/服务层显式做规范化与比较**，而不是依赖排序规则：
  - 业务编码、SKU 编码、设备标识在写入前 `strip()`，并以 `casefold()` 结果做重复性业务校验。
  - 对外查询的精确匹配使用数据库唯一约束兜底，同时服务层给出明确冲突提示。
- 已知限制：若未来需要「`Abc` 与 `abc` 视为不同编码」，必须改为 `_bin` 排序规则并重建索引，
  属于破坏性变更，需单独评审。当前业务语义为**不区分大小写**，故 `_ai_ci` 语义满足需求。
- 关闭条件：随阶段 2 单据编号落地时补充「同码不同大小写」的专项测试用例。
  **部分关闭**：供应商资质证书编号已按此语义落地并有用例覆盖（`test_srm_api.py::test_qualification_certificate_no_deduplicated_case_insensitively`），
  单据编号的大小写用例仍待阶段 2 单据落地后补充。

## 四、业务与数据边界假设

1. **单企业、多工厂、多部门**。数据模型保留 `company_id` 归属，但**不宣称已完成 SaaS 多租户隔离**。
2. 库存维度中的「无批次 / 无卷号」等空值场景，**不使用含多个可空字段的联合唯一索引防重**，
   改用显式规范化维度键（见 `docs/data-model.md` 与 `docs/inventory-rules.md`）。
3. 时间统一按 UTC 存储（`USE_TZ=True`），业务界面按 `Asia/Shanghai` 展示与分组。
4. 阶段 0/1 的演示数据均为**开发种子数据**，界面与接口中一律带有模拟标识，不得当作真实业务数据。
5. 设备采集在阶段 5 实施前，**不存在任何真实硬件接入**；平台内不提供伪造的采集结果。
6. **「同一客户/供应商只能有一个主联系人」由服务层保证，不是数据库约束**：
   MySQL 不支持带条件的部分唯一索引（`UniqueConstraint(condition=...)` 在 MySQL 上不被支持）。
   规则实现在 `apps/core/services.py::ensure_single_primary`，与写入同事务执行，
   并由 `test_crm_api.py` / `test_srm_api.py` 覆盖。**不对数据库层做虚假承诺**。
7. **供应商资质证书编号的判重语义为「不区分大小写」**：`dedup_key` 使用 `casefold()`
   规范化；未填写编号时 `dedup_key` 为 `NULL`，同类型可并存多条。
   若项目方要求区分大小写或禁止重复登记同类型资质，需修改规范化函数并重建唯一索引（破坏性变更）。
8. **`tags`（标签）字段暂不提供界面编辑入口**：模型与接口支持字符串数组，
   但前端通用表单尚不支持数组字段。为避免「看着能填、实际不生效」的假输入，
   界面上不展示该字段；需要界面维护时再单独开发数组控件。
9. **供应商评分/准入审批未实现，界面上也不展示任何评分数值**：
   避免用默认值或空值冒充评价结果（任务书 10.4 规则）。
   准入状态当前只是档案字段，**不代替审批记录**。

### 供应商评价的实施口径（先约定，落地时按此实现）

10. **权重总和必须为 100%**：质量、技术、响应、交付、成本五类权重保存为配置，
    保存与启用时校验总和为 100%；权重版本变更需留痕，历史评分沿用评分时的权重快照。
11. **必须保存评分依据**：每条评分记录保存打分人、时间、原始观测值（如到货准时批次数、
    检验不合格批次数）与计算过程，不允许只存一个最终分数。
12. **无数据不得自动记零分**：某维度缺数据时，按配置选择「标注缺失」或
    「重新分配有效权重」，二者都必须在该条评分记录上体现，且对外展示时标注存在缺失维度。
    不允许把「没有数据」与「数据为零」混为一谈。
13. **停用供应商不能新建正常采购订单**：停用（`is_active=false`）或准入状态非「已准入」的供应商，
    在采购订单服务中校验拦截；确需例外时走显式授权并留痕。
    该校验点落在采购模块，当前采购模块尚未实现，校验随之落地。


## 四之二、库存服务的实现假设（阶段 2 核心）

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-06 | 调整单（`adjustment`）**复用修正（`ST`）编码规则**，未新增 `AD` 规则 | 避免在编码规则表中增加仅为区分类型存在的规则；若业务需要单独的盘点/调整号段，需新增规则并回填历史单据 |
| A-07 | 批次号/卷号**不区分大小写**（`casefold()`） | 符合任务书 5.1「明确大小写是否敏感」的要求；已文档化并测试（`test_batch_no_is_case_insensitive`）。若业务上存在区分大小写的合法批次，需改为保留原样 |
| A-08 | 冲销（`reverse`）采用「**原单反向流水 + 状态标记**」，不修改原流水 | 符合任务书 5.5「不做原地改数」；冲销前必须确认下游未消耗，否则拒绝 |
| A-09 | 库存余额**只保存数量，不保存金额** | 移动加权平均属阶段 7 「基础成本」；本轮不伪造已完成成本核算 |
| A-10 | 服务层**始终拒绝负库存**，忽略 `Warehouse.allow_negative_stock` | 字段已建模但未接入判定；若要开放，必须补充显式授权与审计，不能仅靠字段放行 |
| A-11 | 跨仓调拨**暂不支持**，调拨以同仓移库实现 | 在途状态与目标仓确认流程尚未建模；不伪造「已实现调拨」 |

## 四之三、采购模块的实现假设（阶段 2 采购增量）

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-12 | `PurchaseOrder.tax_rate` 采用**百分数**（0~100），不是小数比率 | 与页面字段「税率(%)」一致，避免 13% 被写成 0.13；若业务要求小数比率，需迁移历史数据并改前端 |
| A-13 | 订单金额按**行金额四舍五入到 4 位小数后求和**，再算税额、价税合计（`ROUND_HALF_UP`） | 明确「舍入发生在哪一步」；与「先合计再舍入」在某些单据上会差 0.0001，如有对账要求需先确认口径 |
| A-14 | **账期/结算方式**只作为文本字段（`payment_terms`），不做账期计算与到期提醒 | 应付与账期管理属阶段 7；本轮不伪造财务能力 |
| A-15 | 收货单**只能引用采购订单行**，不支持无订单的「直接收货」 | 保证「实收到货」都有来源可追溯；若存在零星采购/无单收货场景，需新增来源类型并单独授权 |
| A-16 | 采购收货**只进一个仓库**（单据头级 `warehouse`），行级可选择储位 | 与「一次到货落一个仓」的实际操作一致；跨仓收货需拆成两张收货单 |
| A-17 | 来料检验是**人工判定**，且一次判定作用于**整张收货单的所有行** | 未接入检测设备，无法取得自动判定；若要按行分别判定（部分合格部分不合格），需改为行级判定并拆分库存单据 |
| A-18 | 收货过账后的待检库存**不参与占用**（`reserved`） | 采购侧到货尚未成为可分配供给；占用由销售订单与工单驱动 |
## 四之四、销售模块与库存占用的实现假设（阶段 2 销售增量）

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-19 | 销售订单的**发货仓库在订单头**（`SalesOrder.warehouse`）；未指定仓库时**拒绝占用与发货** | 占用必须落到明确的仓库维度；若要「按订单行指定仓库」，需改为行级字段并同步占用、出库与退货逻辑（错误码 `ORDER_WAREHOUSE_REQUIRED`） |
| A-20 | 占用维度（储位 / 批次 / 卷号）由 `stock.choose_reservation_dimension` **自动挑选可用量最大的合格维度**；同一物料分散在多个维度时报 `STOCK_SPLIT_ACROSS_DIMENSIONS` | **不做跨维度自动拆分占用**，避免「一次占用写多行」带来的部分失败与释放规则复杂化。如需自动拆分，必须新增可追溯的分配模型并重新定义释放口径 |
| A-21 | 销售发货**必须先占用**（出库一律 `require_full_reservation=True`） | 保证「已承诺给某订单的数量」不会被别的订单抢走；未占用直接发货返回 `RESERVATION_REQUIRED`。这比任务书要求更严，若业务上希望「先到先发」，需显式降级并说明 |
| A-22 | 占用**不写库存流水**，一致性口径为 `InventoryBalance.reserved == 该维度未结占用之和` | 流水只记实存量增减，便于对账；占用结束区分 `closed`（被消耗）与 `cancelled`（被释放），可追查「占用去哪了」 |
| A-23 | 退货行未填储位 / 批次 / 卷号时，**继承原发货出库单据的维度并写回退货行** | 批次追溯不断链，检验放行复用同一维度；若原发货行维度为空（历史数据），退货会因维度不全被拒绝，需人工补齐 |
| A-24 | 可退数量按**「已发货 − 已退货」总量**控制，不按批次分摊 | 首版不建模「退回的是哪个批次的货」，多批次部分退货的批次级分摊留待后续；当前以继承原发货维度为准 |
| A-25 | 销售订单**未建模折扣与订单变更版本快照**（只有单价 + 税率，金额后端算） | 任务书 10.3 的折扣、订单变更版本快照未实现，**不伪造**；已列入 `docs/progress.md` 与本文档 §六未做清单 |

## 四之五、BOM 与工艺路线版本快照的实现假设（阶段 3 第一步）

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-26 | 含损耗用量口径为 `gross_quantity = 净用量 × (1 + 损耗率)`，损耗率取值 `[0, 1)` | 任务书 9.5 只要求「标准用量、损耗」，未定义公式方向。另一常见口径是 `净用量 ÷ (1 − 损耗率)`（结果更大）。若企业实际按后者，**只需改 `BomLine.gross_quantity` 一处**（舍入已收敛在该属性内），但历史版本的已下达工单快照不会自动重算，需人工评估 |
| A-27 | 「同一款式/SKU 范围同时只有一个生效版本」由**服务层**保证（`transaction.atomic()` + `select_for_update`），不依赖数据库索引 | MySQL 没有部分唯一索引（`UNIQUE ... WHERE status='approved'`），无法用索引兜底。风险：绕过服务层直接改 `status` 会破坏该约束；已通过「模型不提供状态写入路径 + 视图必须走服务」约束，但**未做并发用例** |
| A-28 | 替代料行**必须**指向同一 BOM 内的正常用料行（`substitute_for`），不建模「整行替换式 BOM」 | 首版按「主料 + 可替代料」表达；若需要「A 方案 BOM / B 方案 BOM」并存，应使用不同的 `scope_key`（SKU 差异版本）或新增方案号字段 |
| A-29 | 工艺路线用文本 `workcenter` / `equipment_requirement` 记录工作要求，暂不与 `factory.Station`、阶段 4 的设备主数据建外键 | 阶段 4 才有设备台账；提前建外键会把未完成的模块耦合进来。阶段 4 落地时补外键并写数据迁移，届时旧的文本字段保留为展示用 |
| A-30 | 工单版本快照**尚未落库**：本轮只提供 `build_bom_snapshot()` / `build_routing_snapshot()` 的不可变输出 | 快照归属方是 MES 工单（阶段 3 后续增量），按任务书 20.3「不建空壳」的要求不预先建空表；因此必测案例 13「BOM 历史快照不受修改影响」当前以「**已审核版本内容不可修改 + 派生新版本后旧快照不变**」的方式验证 |

## 四之六、MRP 的实现假设（阶段 3 第二步）

> 编号接 §四之五 的 A-30，从 **A-31** 开始。这些假设同时写在 `MrpRun.parameters` 快照里，
> 因此历史运行可以复现当初口径（`docs/data-model.md` §三 planning）。

| 编号 | 假设 | 理由与影响 |
| --- | --- | --- |
| A-31 | **批量规则为 lot-for-lot**：净需求多少就建议多少，**不做批量合并**、**不设安全库存缓冲**、**无提前期**（需求日期即建议交期） | 首版没有供应商交期与产能约束数据，凭空设置提前期会伪造准确性。影响：建议可能高于实际最优批量；后续接提前期/批量规则时，只需在净算处新增规则层，历史运行快照不受影响（`parameters.lead_time_mode` 已固化为 `lot_for_lot`） |
| A-32 | MRP 的**需求来源只有销售订单**（`demand_sources=['sales_order']`），生产计划 / 预测 / 安全库存补货均不产生需求 | 销售模块已在阶段 2 第四步落地，是唯一有真实数据的来源。影响：MRP 结果只反映已批准订单，不是完整供需平衡；新增来源时需在 `_collect_demands()` 增加分支并同步 `parameters` |
| A-33 | **在制供给恒为 0**：枚举 `MrpSupplySource.IN_PROGRESS` 已定义，但当前不产生任何供给行（`in_progress_supply='not_implemented'`） | MES 工单未实现，没有任何可信的在制数量。**刻意不伪造**在制，否则会把不存在的产能当成可用供给，导致漏采购 |
| A-34 | 替代料**不参与净算**：BOM 展开只取 `line_type=normal` 的行（`include_substitutes=false`） | 替代料是否可用取决于现场与实际库存，盲目把替代料计入供给会低估缺料。影响：有替代料方案的物料会显示为缺料，需人工按替代方案处理 |
| A-35 | 展开用量取 **`gross_quantity`（含损耗）**，不做二次损耗叠加 | `gross_quantity = 净用量 ×(1+损耗率)`（见 A-26），含损耗用量已经是"生产 1 件实际要投的量"。影响：若企业损耗口径是按工序累计而非单行，需要改为路线级损耗模型 |
| A-36 | **可用量 = `on_hand − frozen − reserved`**，且**只统计 `quality_status=qualified`** 的库存（`frozen_and_reserved='excluded_from_available'`） | 冻结与占用是"已被承诺/被锁定的量"，不能再次作为自由供给；待检 / 不合格库存不能直接投产或销售（任务书 10.8）。影响：MRP 与销售的占用口径必须保持一致，`docs/inventory-rules.md` 为唯一口径来源 |
| A-37 | **生产建议不生成 MES 工单**，`convert_suggestion()` 直接返回 `PRODUCTION_ORDER_NOT_IMPLEMENTED` | MES 属阶段 3 第三步。若先建"占位工单"，会产生无 BOM 快照、无工艺、无派工的假单据，违反任务书 20.3。影响：生产建议当前只能线下评审 |
| A-38 | 采购建议转单只创建**草稿**采购申请，**不自动提交审批**、**不直接生成采购订单** | 审批与库存/采购承诺是不同动作（任务书 10.1）。影响：转单后仍需人工提交与审批；这是刻意设计，不是缺陷 |
| A-39 | **默认需求区间 90 天**（`DEFAULT_HORIZON_DAYS=90`），`bucket=week` 时分段键**归一到周一** | 服装企业常见备料周期；区间与分段均可由调用方指定并写入快照。影响：超出区间的需求被忽略（`test_demand_outside_horizon_ignored`），需要更长区间时显式传参 |
